# 验证体系重构：认证（原验证系统更名）＋ 新增安全验证（Step-up）

日期：2026-10-18

原「验证系统」（邮箱 / 人工 / 委任 / 认证码四通道 + 有效期）更名「**认证系统**」——术语全量替换、代码标识冻结（`Verification` / `is_verified` / `/auth/verification/*` 不动，先行的改名 PR）。「验证」一词随之让位给本文档的新系统：**安全验证**——敏感操作前确认「是本人」。

## 决策

1. **双系统分工**：**认证**回答「账号是不是可信社员」（低频、入社时、四条通道 + 有效期）；**安全验证**回答「现在这个操作是不是本人」（每次危险操作前的二次确认）。两者正交、互不授权——认证不产生验证凭证，验证不改变账号身份态。
2. **验证方式（P1）**：① **邮箱验证码**——只发**已认证邮箱**（`User.email`，即邮箱认证晋升后的地址；未认证邮箱不可用）；② **安全问题**——**预设题库**（10 题，不出自定义题，防「答案写在题干里」），每账号 1–3 题，答案归一化（NFKC 全半角 / 去空白 / 大小写折叠）后 `make_password` 哈希；验证时抽 1 题作答。方式可扩展（TOTP 等预留）。
3. **作用域（scope）**：`change_password` / `manage_questions` / `change_email`（枚举可扩展：新动作接一个 scope 即接通架构）。
4. **令牌（grant）**：验证通过签发 Django signing 令牌（账号 + scope + 时间戳），**TTL 10 分钟**；服务端**无状态、不入库**，不引入状态清理；前端存 sessionStorage、随受保护请求带 `X-StepUp-Grant` 头；**同 scope 窗口内复用**（免连环复验）。缺令牌 → `403 {"reason": "step_up_required", "scope": …}`；前端统一跳 `/#/verify?action=<scope>&next=…`，完成后回跳、重试原操作。
5. **受保护动作（P1）**：改密码＝**原密码 ＋ grant**（原密码证「知道旧密」，验证证「是本人」，两者都要）；邮箱**换绑**＝grant（**首次绑定不拦**，否则新用户死锁）；安全问题管理：**首设＝重输登录密码**（防「偷到会话但没有密码」的人自设验证方式再改密码），更换 / 清除＝grant。
6. **规格**：邮箱码 6 位 / TTL 10 分钟 / 同码最多试 5 次 / 60 秒重发冷却 / 每小时上限（账号 + IP 双通道，入站点策略）；安全问题连错 5 次锁 10 分钟；错误统一文案（不泄露细节）；发送端点失败按双通道节流。
7. **审计**：`StepUpEvent`（谁 / 何时 / 哪方式 / 成败 / IP）——个人中心「安全验证」可查最近记录。
8. **会话保持（实测钉住）**：改密成功须 `update_session_auth_hash`（会**轮换 session key**）**并同步**单会话中间件的 `UserSession` 行——否则自己的新会话会被判「他设备登录」而挤下线；e2e 以「改密 → 跳验证 → 作答 → 回跳重试 → 免复验改回」全链路守住。

## 被否的方案

- **仅原密码确认（不加验证）**：原密码 ≠ 「是本人」的强证据（撞库 / 密码复用 / 会话被偷场景失效）。否。
- **把安全验证并入认证系统**：认证是「身份态」（低频、有有效期、改身份）；安全验证是「操作确认」（每次、无状态令牌）；混在一起会让认证的失效语义与操作频控互相污染。否。
- **自定义安全问题**：答案常就写在题干里，且审核成本高；预设题库可控。否。
- **服务端入库存 grant**：无状态签名已够（10 分钟、单 scope）；入库要清理、要状态机，收益为零。否。
- **每次操作都要求验证（无复用窗）**：改密后紧接着「换绑邮箱」这类连环操作会反复打断；10 分钟同 scope 复用为体感与安全的折中。否（保留复用窗）。

## 兼容与迁移

- 认证系统仅**文案改名**（代码标识 / URL / 字段 / 表名冻结）；本 PR 新增模型三张（`SecurityQuestion` / `StepUpEmailCode` / `StepUpEvent`，accounts 0018）与策略两项（common 0012）。
- Bootstrap：无任何可用方式时给出引导（邮箱→先认证；问答→设置），**不提供「仅原密码」回退**（否则安全验证失去意义）；实在走不通 → 联系信息组。
