# 邮箱后缀白名单（只接受认可的服务商域名与中国院校域）

日期：2026-10-11

## 背景

邮箱是账号的第二联系面：验证信、密码重置、通知转发都发往绑定邮箱。站点用第三方
邮箱（``EMAIL_HOST_USER`` 指向的 163 邮箱）发信，到达率取决于收信方。

放开任意后缀的后果是支持成本不可控：成员填一个自建域 / 冷门域的地址，验证信被退信或
进垃圾箱，成员只看到「邮件没收到」，管理员无从排查；也会放大「随便填个邮箱占位」的行为。

同时，成员实际在用的邮箱高度集中：网易（163 / 126 / yeah）、QQ（qq / foxmail）、
微软 Outlook、Apple iCloud（含「隐藏我的邮件」转发地址）、三大运营商（移动 139 / 联通沃 /
电信 189、21CN）、新浪；在校学生则常用学校邮箱（大陆 ``xxx.edu.cn``、
港澳 ``edu.hk`` / ``edu.mo``、台湾 ``edu.tw``）—— 院校地址同样是「真实本人」的强信号。

## 决策

1. **内置白名单，分两类判定**（``accounts/email_domains.py``）：
   - **商业服务商域**（``PROVIDER_DOMAINS`` → ``ALLOWED_EMAIL_DOMAINS``）：**精确匹配**
     （``evil163.com`` / ``163.com.evil.com`` 不放行）；
   - **中国院校域**（``EDU_DOMAIN_SUFFIXES``）：**域自身或其子域**均放行。高校无法穷举
     （一校一个域，学生信箱还常在 ``stu.`` / ``mails.`` / ``smail.`` / ``connect.`` 等更深子域），
     故对 ``edu.cn`` / ``edu.hk`` / ``edu.mo`` / ``edu.tw`` 按后缀放行；学生信箱不在
     ``edu.*`` 下的院校逐校列入（校名见代码注释）。
   名单是**代码级策略**：不接受用户输入、不做后台可编辑项（避免被改宽后无人知晓），
   改动走 PR + 重新部署。
2. **判定只发生在「接收新地址」的两处**：注册带邮箱（``register_view``）、验证面板绑定 /
   换绑（``verification_email_bind_view``）。
3. **被拦时**：HTTP 400 + ``reason="email_domain_not_allowed"`` + ``domain`` + 固定文案
   ``该邮箱后缀暂不可用，请换用其他邮箱。详询社长或服务器管理员``。前端据 ``reason`` 映射成
   类型化 ``email_domain_not_allowed``，用 ``NoticeModal`` 弹窗打断（不做行内小字，避免被忽略）。
4. **不回溯（祖父条款）**：
   - 已绑定 / 已通过的旧地址不作废，同址重发 / 复绑照旧放行；
   - ``/auth/resend-verification/`` 不校验域名（只重发既有 pending 地址，不改地址）；
   - 验证链接落地（``/auth/verify-email/``）不校验域名（令牌已限定为既有 pending 地址）；
   - Django admin 里管理员手填的邮箱不校验（管理与应急通道保持畅通）。
5. **未覆盖的自建域**（公司域、未列入的中科院各所 ``@xxx.ac.cn``、部分自资院校）不在名单内；
   这类成员走人工审批或认证码通道完成验证（已有通道，无需新机制）。

## 后果

- 成员注册 / 绑邮箱时若用了 gmail 等域名，会立刻收到弹窗提示改邮箱 —— 反馈在提交当刻，
  不会拖到「等不到验证信」才发现；校园邮箱（含学生信箱子域）可直接绑定通过。
- 院校域按后缀放行是刻意的取舍：宁可多放「同一所学校的学生信箱子域」，也不要为穷举子域
  把名单维护成无底洞；``edu.cn`` / ``edu.hk`` / ``edu.mo`` / ``edu.tw`` 是受注册限制的
  国别教育域（注册方须为教育机构）。
- 白名单是硬编码常量：新增服务商 / 院校需要一次改动 + 部署（换来的是「谁放开的、什么时候」
  有据可查）；加一行即可，无需改判定与前端。
