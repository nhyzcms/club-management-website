# ADR-0029：账号安全中心（设备信任 / 登录挑战 / 滚动密钥）

- 状态：已采纳（2026-10-24）；P0–P4 已实现（PR #189–#192），P5 通行密钥待域名 + HTTPS
- 相关：[ADR-0026](0026-stepup-verification.md)（安全验证 Step-up）、[ADR-0028](0028-multi-device-login.md)（多端登录）

## 背景

改密码、安全问题与登录记录原本散落在个人主页的三个标签页，登录侧只记「会话」不记「设备」：没有设备列表、没有登录事件流水、也没有「这是不是本人常用设备」的概念。账号密码在同学之间共享时，本人无法从界面上察觉「有别人在用」；邮箱未绑定的账号也缺少可用的二次验证方式。

参考微软账户「安全性」页，产品决定新增**账号与安全中心**（`/#/security`），把登录方式、设备与登录记录收进一处，并为登录增加「陌生设备二次验证」与「滚动密钥（TOTP）」。

## 决策

### 1. 设备身份 = 服务端签发的随机 ID

设备 ID 由服务端生成（32 位 hex），写入 HttpOnly、2 年有效的 `club_device` Cookie。它与硬件标识无关——浏览器没有任何 API 能读 MAC 地址；品牌 / 型号只能从 UA 与 User-Agent Client Hints 尽力推断，允许为空。

`AccountDevice` 以 `(user, device_id)` 唯一；`UserSession.device_id` 复用同一个 Cookie 值，不另建设备 FK。删掉 Cookie 等于设备回到陌生态，这是预期行为而不是缺陷。

### 2. 信任的唯一来源是二次验证

**所有设备初始都是陌生设备。** 设备的 `trusted_at` 只在「该设备上完成过一次有效的二次验证」时写入。指纹、IP、地理位置、UA 一致性都不构成信任，也不参与跳过验证。

- 清 Cookie / 换浏览器 → 陌生；
- 用户撤销设备 → 陌生；
- 通过 TOTP / 邮箱码 / 安全问题 / 恢复代码任一 → 信任，默认永久（`trusted_at` 记录时间），直到用户撤销。

### 3. 陌生设备登录返回 202 挑战，不建会话

密码校验通过后，若设备陌生且账号有可用的二次验证方式，`POST /auth/login/` 返回 **202** + `{challenge, methods, questions, reason: "new_device", expires_in}`，**不建立 session**。挑战令牌 10 分钟有效、最多失败 5 次；通过后建 session，并把设备标为 trusted。

账号**没有任何二次验证方式**时，本次豁免放行：响应带 `must_bind_2fa=true`，设备保持陌生，前端引导去 `/#/security` 绑定。豁免不等于信任——下次登录仍会要求。

`LOGIN_CHALLENGE=0` 可关闭挑战流程（设备与事件记录不受影响），用于线上异常时的应急回滚；`manage.py test` 下自动关闭，避免既有登录用例被迫走挑战。

### 4. 滚动密钥（TOTP）与恢复代码

- RFC 6238：HMAC-SHA1 / 30 秒 / 6 位，允许 ±1 时间窗；每条记录独立的 `last_used_step` 防重放；
- 每个账号最多 5 个 TOTP，每个独立 secret；secret 用 Fernet 加密入库（密钥由 `SECRET_KEY` 派生）；
- 首次确认 TOTP 时生成账号级 10 个恢复代码，只存 sha256、一次性；重新生成作废旧码；
- 解绑 TOTP / 重新生成恢复代码需要 Step-up（`manage_totp`），防止会话被劫持后直接摘掉二次验证；
- TOTP 与恢复代码当前只用于登录挑战，不作为 Step-up 的验证方式（Step-up 仍是邮箱码 / 安全问题）。

### 5. 登录事件与城市级位置

每次登录都写一条 `LoginEvent`（成功 / 失败 / 被限流 / 待验证），记录账号、设备、方式、二次验证、IP、UA、城市与坐标；账号不存在时 `user` 为空，仍保留 IP / UA 供风控分析。

位置由离线 **ip2region** 库解析（`data/ip2region_v4.xdb`，约 11 MB，不入 git，可用 `IP2REGION_DB` 覆盖）；库缺失或损坏时静默降级为只记 IP。坐标取内置城市中心点表，**只到城市级**，移动网络可能落到运营商出口城市。

前端地图用高德 JS API，构建时 `AMAP_KEY` 经 webpack `DefinePlugin` 注入；无 key 时降级为城市文字。

### 6. 页面与旧入口

新增 `/#/security`（`SecurityCenterPage`）。个人主页原有的 `?tab=security` / `password` / `sessions` 一律 `replace` 到新页，旧链接保持可用；`/#/verify` 继续作为 Step-up 执行页。

### 7. 管理端只读 + 访问留痕

Django Admin 新增三张只读表：登录事件、账号设备、管理端访问记录。设备信任状态不允许在后台手改；打开登录事件 / 设备列表的 changelist 会写一条 `AdminAccessLog`（谁、看了谁、何时、从哪个 IP），监控权本身也可审计。

## 后果

- 密码泄露后，攻击者在陌生设备登录必须再过一道二次验证；本人能在安全中心看到设备与登录记录并撤销设备。
- 所有既有社员设备上线后都是陌生设备：有二次验证方式的会走一次挑战，没有的本次豁免并收到绑定提示。
- 无 2FA 的账号仍可登录（不锁号），但每次换设备都会提示绑定——这是「不强制」与「可察觉」之间的折中。
- 登录请求多一次设备查询与事件写入；地理位置解析走本地 xdb，无外部请求。
- 设备列表与登录事件属于账号资产，管理员可见、不可改；完整 IP 仅在 Django Admin（staff）可见，本人界面脱敏。

## 不采用 / 未做

- **采集 MAC 地址**：Web 端不可能，界面不展示。
- **街道级 / GPS 定位**：IP 只能到城市，不提供更细位置。
- **短信验证码**：无短信通道，成本与合规不划算。
- **Passkey（P5）**：WebAuthn 的 RP ID 不能是 IP，当前生产环境没有域名 + HTTPS，暂缓。
- **管理员代替用户验证 / 后台手改设备信任**：只读，不提供冒充能力。
- **登录事件自动清理**：设计稿默认 180 天，目前尚未实现定时清理任务。
